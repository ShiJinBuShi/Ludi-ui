# 扩展约定

## 知识与运行包的边界

`skills/zh-CN/ludi-ui` 与 `skills/en/ludi-ui` 各自自包含。入口负责触发、流程和路由，引用负责场景判断，模板负责重复产物。`manifest.json` 是结构与双语对齐的契约，不要求 agent 每次 UI 任务都读它。根目录原稿、维护工具和评估材料不属于运行时必读内容。

同一知识只有一个主要维护位置，其他模块用链接引用，避免多处抄写后逐渐冲突。框架专用知识确有需要时可新增 `react-forms.md` 等模块，并明确触发条件；不要把 React 专属实现写成所有前端通用规则。

## 新笔记进入技能的流程

1. 记录原始来源、作者/链接（已知时）、日期、适用产品和证据边界；无来源的经验按经验处理，不包装为标准。保持原始材料与可执行规则分开。
2. 对照现有规则 ID 去重。新材料只是补充例外/条件时更新原规则；不同任务才新增模块。冲突时区分平台差异、产品选择、过期实现及真正错误，不机械拼接。
3. 按 [knowledge-module.md](../skills/zh-CN/ludi-ui/templates/knowledge-module.md)编写：问题 → 判断条件 → 实施行为 → 例外/回退 → 可观察验证。源稿中的固定数值要说明适用依据。
4. 同步两种语言的模块、规则 ID 与等级，补充两个清单。每个模块对象由 `id`、`path` 和 `rules` 组成，规则映射值只能是 `contract`、`default` 或 `optional`。
5. 在两个入口增加场景路由，更新两个来源页及相关行为案例。较长内容按独立场景拆分；入口不积累所有细节。
6. 运行结构/缺陷注入测试，再评审语义和行为。版本、规则 ID、路径一致不代表翻译和判断自动正确。

## 结构示例

假设增加已完成双语编写的表单模块，在两份清单 `modules` 中加入：

```json
{
  "id": "forms",
  "path": "references/forms.md",
  "rules": {
    "FORM-01": "contract",
    "FORM-02": "default"
  }
}
```

文件中使用 `## FORM-01 · 失败后保留输入` 等稳定标题，下一段写 `**Contract（契约）。**`；英文对应 `**Contract.**`。这是一条格式契约，让校验器能核对标题和等级，不要求中英文标题逐字对应。模块必须在入口被链接。不要提交只有标题或模板占位内容的模块。

## ID 与版本

- 模块 ID：小写单词加连字符；文件路径大小写精确，包内链接不得越出语言包。
- 规则 ID：英文大写/数字前缀加数字，如 `AI-01`、`A11Y-02`。现有 ID 不改号、不复用；删除时在本页记录退役和替代，两个语言包同步变更。
- 修订措辞/错误用 patch；兼容地新增场景用 minor；删除规则、改变等级含义或要求不兼容工作流用 major。两份入口 metadata 与清单版本同步。
- `schemaVersion` 是维护格式版本；改变清单形状时同步升级校验器和测试，不能只改技能版本。

## 维护检查

```powershell
node tools/validate.mjs
node --test tests/validate.test.mjs
```

新行为案例放在 `evals/cases.json`，含双语请求、适用规则与可观察通过条件。独立评估时只给请求、所选语言 skill 和必要样例，不提供预期答案；在隔离目录执行有副作用的任务。记录 agent、版本、环境、结果与未测试项。现有验证报告仅代表记录的场景，不自动覆盖新增模块。

校验器检查结构，不判断 UI 美观、双语语义或 WCAG 全面符合性。引入可执行脚本或框架样例前先说明重复使用价值，并真正运行；普通建议无需为了“工程感”新增程序和依赖。

## 发布分发包

修改运行包后，`dist/` 中的旧 ZIP 不会自动更新。完成校验和行为评审后，按新版本分别压缩两个完整 `ludi-ui` 目录，保留压缩包顶层 `ludi-ui/`；文件名使用 `ludi-ui-版本-语言.zip`。核对压缩包内的文件集合及逐文件内容与源目录一致，再重新生成 `SHA256SUMS`。根目录原稿、评估样例和维护工具不放入运行包。

结构校验默认检查源目录，不能单独证明已发布 ZIP 与当前源码同步。更新 README 中的版本、计数和分发链接，重新记录实际验证证据，不沿用旧报告声称新增知识已通过行为验收。
